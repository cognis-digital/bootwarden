## 3. UEFI Module Signing and Verification Mechanisms

### UEFI Firmware Signing Architecture Overview

UEFI firmware signing architecture is a layered mechanism designed to ensure the integrity and authenticity of UEFI modules, including the core firmware, drivers, and applications. At its core, this architecture leverages cryptographic signatures and a hierarchical trust model to verify that each component has been authorized by a trusted entity. The signing process begins with the firmware manufacturer, who generates a private key pair and uses it to sign the firmware image. This signature is then validated during the boot process using a public key stored in the platform’s trusted root of trust, typically within the UEFI firmware itself or in secure hardware such as a Trusted Platform Module (TPM). The signing architecture is further extended through the use of certificates, which provide a chain of trust from the manufacturer to the end-user. These certificates are often embedded in the firmware and used to validate the authenticity of the signed modules during runtime.

The signing process is governed by a set of cryptographic algorithms and protocols that define how signatures are generated, stored, and validated. The most commonly used algorithm for UEFI firmware signing is RSA with SHA-256 or SHA-384 as the hash function, although elliptic curve cryptography (ECC) is also gaining traction in modern firmware implementations. The private key used for signing is typically stored in a secure portion of the firmware, such as a dedicated Secure Boot Key (SBK), which is protected against tampering and unauthorized access. The corresponding public key is then embedded in the firmware or stored in a trusted hardware module, enabling the platform to verify the authenticity of the signed modules during the boot process.

The UEFI firmware signing architecture also incorporates a mechanism known as the "Secure Boot" feature, which is a key component of the Unified Extensible Firmware Interface (UEFI) specification. Secure Boot ensures that only firmware and operating system components signed by trusted authorities can be loaded during the boot process. This is achieved through a chain of trust that begins with a root-of-trust certificate stored in the firmware or hardware. The root certificate is used to validate intermediate certificates, which in turn are used to validate the signatures on individual firmware modules. This hierarchical structure allows for flexibility in managing firmware updates and ensures that even if a lower-level component is compromised, the higher-level components remain trustworthy.

In addition to cryptographic signing, the UEFI firmware signing architecture includes mechanisms for managing the lifecycle of keys and certificates. Key management is critical to maintaining the integrity of the signing process, as compromised keys can lead to unauthorized modifications of firmware modules. The firmware manufacturer is responsible for generating and securely storing the private key used for signing, while the public key is embedded in the firmware or stored in a trusted hardware module. The key lifecycle includes generation, distribution, usage, revocation, and destruction, all of which must be carefully managed to prevent key leakage or misuse.

The firmware signing architecture also supports the use of certificate chains, which allow for the delegation of signing authority. This is particularly useful in scenarios where multiple entities are involved in the signing process, such as a manufacturer signing firmware that includes third-party drivers or applications. In such cases, the root certificate is used to validate an intermediate certificate, which in turn validates the signature on the final firmware module. This approach ensures that even if a third-party component is compromised, the overall trust chain remains intact as long as the root certificate remains secure.

The UEFI firmware signing architecture also incorporates mechanisms for handling firmware updates. When a firmware update is released, it must be signed using the manufacturer’s private key to ensure its authenticity. The update process typically involves verifying the signature of the new firmware image against the stored public key before applying the update. This verification step ensures that only authorized firmware can be installed, preventing unauthorized modifications or malicious payloads from being introduced into the system.

Another important aspect of the UEFI firmware signing architecture is the use of secure boot modes, such as UEFI Secure Boot and Legacy Secure Boot. These modes provide different levels of trust and validation for firmware components. UEFI Secure Boot, for example, requires that all firmware modules be signed by a trusted certificate authority (CA), while Legacy Secure Boot may rely on a simpler model where the firmware is signed using a single key. The choice of secure boot mode depends on the specific requirements of the platform and the level of trust required for the firmware components.

The architecture also includes mechanisms for handling errors and exceptions during the signing process. For instance, if a firmware module fails to validate its signature, the system may halt the boot process or prompt the user to resolve the issue. These error-handling mechanisms are critical for ensuring that only valid and trusted firmware components are loaded, thereby maintaining the integrity of the system.

In summary, the UEFI firmware signing architecture is a complex but well-defined mechanism that ensures the authenticity and integrity of UEFI modules. By leveraging cryptographic signatures, certificate chains, and secure key management, this architecture provides a robust foundation for verifying the trustworthiness of firmware components during the boot process. The use of Secure Boot and other secure boot modes further enhances this trust model by ensuring that only authorized firmware can be loaded, thereby protecting the system from unauthorized modifications and malicious attacks.

### Secure Boot Key Management and Chain of Trust

Secure Boot Key Management and Chain of Trust

Secure Boot is a critical component of the Unified Extensible Firmware Interface (UEFI) that ensures only trusted firmware components are loaded during the boot process. At its core, Secure Boot relies on a hierarchical key management system to establish a chain of trust from the firmware to the operating system. This system begins with a set of pre-installed keys known as the "Platform Key" (PK), which is stored in the UEFI firmware and used to verify the authenticity of the UEFI firmware itself. The PK serves as the root of trust, and its integrity is paramount to the entire Secure Boot process.

The next layer in the chain of trust involves the "Key Exchange Key" (KEK), which is typically pre-installed by the system manufacturer or vendor. The KEK is used to verify the authenticity of the "Secure Boot Key" (SK) and other keys that are added to the system after manufacturing. Unlike the PK, which is fixed and cannot be easily replaced without reprogramming the firmware, the KEK can be updated through the firmware interface, allowing for the addition or removal of trusted keys. This flexibility is crucial for managing key lifecycles, especially in environments where new keys need to be added or revoked over time.

The Secure Boot Key (SK) is a critical element in the chain of trust, as it is used to sign the operating system loader and other firmware modules that are loaded after the initial boot. The SK must be signed by the KEK to be considered trusted, ensuring that only components signed with keys approved by the system manufacturer can be executed. This process creates a layered verification mechanism where each key in the chain must be validated against the previous one, thereby reducing the risk of unauthorized firmware execution.

One of the most significant vulnerabilities in Secure Boot key management is the potential for key compromise. If an attacker gains access to the KEK or PK, they could sign malicious firmware modules that would bypass the Secure Boot verification process. This has been demonstrated in several real-world attacks, such as the "LoJax" malware, which exploited a vulnerability in the Secure Boot mechanism by using a compromised KEK to load a malicious bootloader. Such attacks highlight the importance of maintaining strong key management practices, including regular key rotation and secure storage of cryptographic keys.

Another critical aspect of Secure Boot key management is the use of Trusted Platform Module (TPM) hardware to store and protect the keys. TPMs provide a secure environment for storing cryptographic keys, ensuring that they cannot be easily extracted or modified by an attacker. The integration of TPMs with Secure Boot allows for hardware-based attestation, where the system can verify the integrity of the firmware before booting the operating system. This hardware-assisted approach enhances the security of the key management process by reducing the risk of key exposure and tampering.

The chain of trust in Secure Boot is also influenced by the use of cryptographic algorithms and key sizes. Modern implementations typically use RSA-2048 or larger for key signing, ensuring that the keys are sufficiently robust against cryptographic attacks. However, the choice of algorithm can impact performance and compatibility, especially in resource-constrained environments. For example, some embedded systems may use smaller key sizes to reduce computational overhead, which could make them more susceptible to brute-force attacks.

In addition to the PK, KEK, and SK, Secure Boot also supports the use of "Measurement Keys" (MeasKey) and "Database Keys" (DBKey) to manage the measurement of firmware components. The MeasKey is used to sign the measurements of firmware modules, ensuring that only trusted components are measured and recorded in the integrity measurement log. The DBKey is used to verify the authenticity of these measurements, creating a closed-loop verification process that enhances the overall security of the system.

The implementation of Secure Boot key management varies across different platforms and vendors, leading to potential inconsistencies in the chain of trust. For example, some systems allow for multiple KEKs to be added, while others restrict this to a single KEK. This variability can create opportunities for attack vectors if not properly managed. A notable example is the "Boot Guard" implementation in Intel processors, which uses a combination of firmware and hardware-based key management to enforce strict Secure Boot policies.

To mitigate these risks, best practices in Secure Boot key management include regular audits of the key hierarchy, secure storage of cryptographic keys, and the use of hardware security modules (HSMs) for key management. Additionally, systems should implement mechanisms for key revocation and replacement, ensuring that compromised keys can be quickly removed from the trust chain. These measures help to maintain the integrity of the Secure Boot process and reduce the likelihood of unauthorized firmware execution.

In conclusion, Secure Boot Key Management and Chain of Trust are fundamental to the security of UEFI-based systems. The hierarchical structure of keys, from the Platform Key to the Secure Boot Key, establishes a robust mechanism for verifying the authenticity of firmware components. However, the effectiveness of this system depends on proper key management practices, including secure storage, regular audits, and the use of hardware-assisted security features. By understanding and implementing these principles, system administrators and developers can significantly enhance the security of their UEFI environments.

### Module Signing Algorithms and Hashing Standards

The module signing algorithms and hashing standards employed in UEFI firmware are critical components of the secure boot process, ensuring the authenticity and integrity of firmware modules. These cryptographic mechanisms form the backbone of the verification process, enabling the system to distinguish between legitimate signed modules and potentially malicious or unsigned ones. At the core of this system are cryptographic hash functions, which generate fixed-size digital fingerprints of module contents, and asymmetric encryption algorithms, which provide the means for signing these hashes with private keys. The combination of these two technologies ensures that each module's authenticity can be verified against a trusted public key, thereby establishing a chain of trust from the firmware to the operating system.

The primary cryptographic hash functions used in UEFI module signing include SHA-256 and SHA-384, which are part of the SHA-2 family of algorithms. These functions produce fixed-length output (256 bits for SHA-256 and 384 bits for SHA-384) regardless of the input size, making them suitable for verifying the integrity of firmware modules. The use of SHA-256 is particularly prevalent due to its balance between computational efficiency and security. However, as cryptographic research advances, newer hash functions such as SHA-3 (Keccak) are being considered for future implementations, offering improved resistance to collision attacks and enhanced performance characteristics. The choice of hash function directly impacts the security level of the module signing process, with longer hash lengths generally providing stronger integrity guarantees but at the cost of increased computational overhead.

In conjunction with hash functions, asymmetric encryption algorithms are employed to sign the hash values generated by these functions. The most commonly used algorithm in UEFI module signing is RSA, which relies on the mathematical properties of large prime numbers for key generation and cryptographic operations. RSA keys typically range from 2048 bits to 4096 bits in length, with longer keys offering greater resistance to factorization attacks. The private key is used to generate a digital signature of the hash value, while the corresponding public key is used to verify the signature during the boot process. This asymmetric approach ensures that only the entity possessing the private key can produce a valid signature, thereby establishing the authenticity of the module.

In addition to RSA, elliptic curve cryptography (ECC) has been increasingly adopted in UEFI firmware for its efficiency and security. ECC algorithms such as ECDSA (Elliptic Curve Digital Signature Algorithm) provide equivalent security to RSA with significantly smaller key sizes. For example, a 256-bit ECC key offers comparable security to a 3072-bit RSA key, resulting in faster cryptographic operations and reduced computational overhead. The adoption of ECC in UEFI module signing reflects a growing trend toward more efficient cryptographic mechanisms that can meet the performance demands of modern firmware environments.

The specific implementation of these algorithms within the UEFI specification is governed by the Unified Extensible Firmware Interface (UEFI) specification, particularly in the context of the Secure Boot feature. The UEFI specification defines the structure and format of module signing keys, as well as the cryptographic operations required for module verification. For instance, the UEFI specification outlines the use of SHA-256 for generating hash values and RSA or ECDSA for signing these hashes. These specifications ensure consistency across different UEFI implementations, enabling interoperability between firmware vendors and operating systems.

The selection of a particular hash function and signing algorithm is influenced by several factors, including the security requirements of the system, the performance constraints of the hardware, and the compatibility with existing infrastructure. For example, in environments where computational resources are limited, such as embedded systems or older hardware platforms, the use of SHA-256 and RSA may be preferred due to their well-established implementation and widespread support. Conversely, in high-performance computing environments or systems requiring advanced security features, the adoption of SHA-3 or ECC-based signing algorithms may be more appropriate.

The integration of these cryptographic mechanisms into the UEFI firmware signing process is further enhanced by the use of standardized key formats and certificate structures. The UEFI specification defines the format of module signing keys, which are typically stored in a trusted key database within the firmware. These keys are used to verify the signatures of modules during the boot process, ensuring that only modules signed with trusted keys are allowed to execute. The structure of these keys and their associated certificates is critical to the overall security of the system, as any compromise of a signing key can result in the execution of unauthorized modules.

In summary, the module signing algorithms and hashing standards employed in UEFI firmware play a pivotal role in ensuring the authenticity and integrity of firmware modules. The use of cryptographic hash functions such as SHA-256 and SHA-384, combined with asymmetric encryption algorithms like RSA and ECDSA, provides a robust framework for secure module verification. These mechanisms are defined within the UEFI specification, ensuring consistency and interoperability across different implementations. By selecting appropriate hash functions and signing algorithms based on security requirements and performance constraints, UEFI firmware can effectively establish a chain of trust from the firmware to the operating system. The ongoing evolution of these cryptographic standards reflects the continuous effort to enhance the security and efficiency of the secure boot process in modern computing environments.

### Verification Process for Signed UEFI Modules

The verification process for signed UEFI modules is a critical component of ensuring firmware integrity and security within the Unified Extensible Firmware Interface (UEFI) architecture. At its core, this process involves analyzing the cryptographic signatures embedded within UEFI modules to confirm their authenticity and origin. The primary mechanism for achieving this is the use of digital certificates, which are typically issued by trusted Certificate Authorities (CAs) or internal root keys maintained by system vendors. These certificates serve as binding entities that link a public key to a specific entity, such as a vendor or developer. When a UEFI module is signed with a private key corresponding to one of these certificates, the verification process confirms that the module was indeed issued by the claimed entity and has not been tampered with since signing.

The verification process begins with the extraction of the signature from the UEFI module. This signature is typically stored in a specific location within the module’s binary structure, often as part of the module header or in a dedicated signature section. The signature includes the module's hash, which is computed using a cryptographic hashing algorithm such as SHA-256. The hash serves as a unique fingerprint of the module's contents, allowing the verification process to detect any modifications that may have occurred after signing. Once the hash is extracted, it is compared against the hash value provided within the signature.

The next step in the verification process involves validating the digital certificate associated with the signing key. This requires checking the certificate chain to ensure that the certificate is valid and has not expired. The certificate must also be trusted by the system, either through a pre-installed root certificate store or via an external trust anchor. In some cases, such as in secure boot environments, the system may rely on a chain of trust initiated by a trusted root key, which is embedded within the firmware itself. This root key is typically stored in a secure location, such as a hardware-backed Trusted Platform Module (TPM), to prevent unauthorized access.

The verification process also involves checking for certificate revocation. This ensures that the certificate has not been invalidated due to compromise or error. Revocation information can be retrieved using mechanisms such as the Online Certificate Status Protocol (OCSP) or the Certificate Revocation List (CRL). In UEFI environments, the use of OCSP is less common compared to CRLs, which are often embedded directly into the firmware image. The inclusion of revocation information in the firmware allows for real-time validation without requiring an external network connection, which is particularly important in environments where network access may be limited or unreliable.

In addition to certificate validation, the verification process must also confirm that the public key used for signature verification matches the one embedded within the certificate. This step involves using the public key to decrypt the digital signature and compare the resulting hash with the computed hash of the module's contents. If the hashes match, the signature is considered valid, and the module is deemed authentic. However, if there is a mismatch, the verification process will flag the module as potentially compromised or unsigned.

The cryptographic algorithms used in the verification process play a crucial role in ensuring the security and reliability of the UEFI module signing mechanism. The most commonly used algorithm for signature generation and verification is the RSA algorithm, which provides strong cryptographic strength and is widely supported across various platforms. Additionally, the use of elliptic curve cryptography (ECC) has become increasingly prevalent due to its efficiency and smaller key sizes compared to RSA. ECC-based signatures are particularly advantageous in resource-constrained environments, such as embedded systems or devices with limited processing power.

The verification process also incorporates the concept of signature chaining, which allows for the validation of multiple signing keys within a single module. This is particularly relevant in complex firmware architectures where modules may be signed by different entities or at different stages of development. Signature chaining ensures that each signature is verified against its corresponding certificate, creating a layered validation process that enhances overall security.

In practice, the verification process for signed UEFI modules is often implemented as part of the firmware's boot sequence. During the boot process, the system performs a series of integrity checks to ensure that all signed modules are valid and have not been tampered with. This includes verifying the signatures of the core UEFI firmware components, such as the BIOS, firmware extensions, and other modules loaded during the boot process. The results of these verifications determine whether the system can proceed with the boot process or if it encounters an integrity failure that may require intervention.

To further enhance the security of the verification process, some systems employ additional mechanisms such as secure boot policies and trusted execution environments (TEEs). Secure boot policies define the criteria for accepting signed modules, including the allowed root keys, certificate authorities, and signature algorithms. These policies are typically configured within the firmware's boot manager and can be customized to meet specific security requirements. Trusted execution environments provide an additional layer of security by isolating critical operations within a secure environment, ensuring that even if a module is compromised, its impact is contained.

In summary, the verification process for signed UEFI modules is a multi-step cryptographic procedure that ensures the authenticity and integrity of firmware components. By validating digital certificates, checking for revocation, and confirming the correctness of cryptographic signatures, the process provides a robust mechanism for securing UEFI firmware against tampering and unauthorized modifications. The use of advanced cryptographic algorithms, secure boot policies, and trusted execution environments further enhances the reliability and effectiveness of this verification process. Through these mechanisms, the UEFI module signing and verification framework establishes a foundation for secure firmware operations, ensuring that only trusted modules are executed during the boot process. The integration of these processes into the firmware's boot sequence ensures that the system maintains a high level of security throughout its operational lifecycle.

### Handling of Unsigned and Unverified Modules

The handling of unsigned and unverified modules within UEFI firmware is a critical aspect of firmware integrity and security. These modules, often referred to as UEFI drivers or components, are essential for system initialization and operation but can pose significant risks if not properly signed and verified. The UEFI specification provides mechanisms to manage these modules, primarily through the use of signature databases and secure boot processes. However, the effectiveness of these mechanisms depends on their implementation and enforcement within the firmware environment.

The UEFI specification introduces the concept of a "signature database," which is used to verify the authenticity of modules during the boot process. This database contains cryptographic signatures of trusted modules, allowing the firmware to validate each component before it is loaded into memory. The primary mechanism for this verification is the Secure Boot process, which ensures that only signed and verified modules can execute during the boot sequence. This process is typically initiated by the firmware's Unified Extensible Firmware Interface (UEFI) implementation, which checks the digital signatures of all modules against the signature database.

One of the key challenges in handling unsigned and unverified modules is the potential for malicious code to be executed if the firmware fails to correctly validate these components. For instance, an unsigned module might be loaded without proper verification, allowing it to execute arbitrary code or modify system settings. This risk is exacerbated when the firmware does not enforce strict signature validation, particularly in environments where multiple modules are involved. In such cases, the absence of a valid signature can lead to vulnerabilities that could be exploited by attackers.

The UEFI specification also outlines the use of "boot services" and "runtime services" to manage module loading and execution. Boot services are responsible for initializing the system and providing a set of functions for module loading, while runtime services handle tasks that continue after the operating system has started. These services play a crucial role in ensuring that modules are properly signed and verified before they are executed. However, the effectiveness of these services can vary depending on the firmware implementation and the specific modules being used.

In addition to signature verification, the UEFI specification includes mechanisms for module loading and execution control. For example, the firmware can enforce policies that restrict the execution of unsigned modules or require additional verification steps before a module is loaded. These policies can be configured through the firmware's settings or through external tools that interact with the UEFI interface. By implementing such policies, the firmware can mitigate the risks associated with unsigned and unverified modules.

The handling of unsigned and unverified modules is also influenced by the firmware's ability to detect and respond to potential threats. For instance, if a module is found to be unsigned or unverified, the firmware may trigger an alert or take corrective action to prevent its execution. This can include logging the event, halting the boot process, or loading a default configuration that ensures system stability. These actions are typically part of the firmware's security policies and can be customized based on the specific requirements of the system.

The UEFI specification also emphasizes the importance of maintaining an up-to-date signature database to ensure that all modules are properly verified. This database is typically stored in a secure location within the firmware, such as a read-only memory (ROM) or a Trusted Platform Module (TPM). The signature database is used to validate each module's digital signature during the boot process, ensuring that only trusted components are executed. However, the effectiveness of this mechanism depends on the firmware's ability to maintain and update the signature database, particularly in environments where new modules are frequently added or modified.

In conclusion, the handling of unsigned and unverified modules within UEFI firmware is a critical aspect of system security. Through mechanisms such as signature databases, secure boot processes, and module loading policies, the firmware ensures that only trusted components are executed during the boot sequence. However, the effectiveness of these mechanisms depends on their implementation and enforcement, highlighting the need for robust security practices in firmware development and management. By addressing the challenges associated with unsigned and unverified modules, the UEFI specification provides a framework for ensuring the integrity and security of the firmware environment. This section has explored the key aspects of handling unsigned and unverified modules, setting the stage for a deeper analysis of related vulnerabilities and mitigation strategies in the subsequent sections.

### SMM Code Signing and Its Verification Challenges

The SMM (System Management Mode) code signing process is a critical component of UEFI firmware security, designed to ensure that only trusted code can execute in SMM. Unlike traditional UEFI modules, which are typically signed using standard cryptographic mechanisms and verified by the UEFI firmware during boot, SMM code operates in a privileged execution environment, often with limited access to verification infrastructure. This makes SMM code signing and its verification particularly challenging. The signing process for SMM code typically involves the use of a private key associated with a secure key store, such as those found in Trusted Platform Modules (TPMs) or other hardware-based cryptographic modules. However, the verification of these signatures during execution is not always straightforward due to the constraints of the SMM environment, which may lack access to certain cryptographic functions or external validation resources.

One of the primary challenges in SMM code signing is ensuring that the private key used for signing remains secure and tamper-proof. If an attacker can compromise the private key, they could potentially sign malicious SMM code, which would then be executed without detection. This risk is compounded by the fact that SMM code often resides in a separate memory region and may not have direct access to the same cryptographic libraries or hardware support as the main UEFI firmware. As a result, the verification process for SMM signatures may rely on simplified or even non-standard cryptographic algorithms, which can introduce vulnerabilities.

Another significant challenge is the lack of standardized verification mechanisms for SMM code. While many UEFI implementations include mechanisms for verifying the integrity and authenticity of modules, these are often tailored to specific hardware platforms or firmware vendors. This variability makes it difficult to ensure consistent security across different systems. For example, some implementations may use a combination of cryptographic hashes and digital signatures, while others may rely on hardware-based attestation mechanisms that are not universally supported. This lack of standardization can lead to inconsistencies in how SMM code is validated, increasing the risk of undetected malicious code execution.

The verification process for SMM code also faces challenges related to performance and resource constraints. Since SMM code operates in a low-level environment with limited memory and processing power, the cryptographic operations required for signature verification must be optimized for efficiency. This often leads to the use of lightweight cryptographic algorithms or even custom implementations that may not provide the same level of security as more robust alternatives. Additionally, the verification process may need to occur without external dependencies, further complicating the implementation.

The SMM environment also presents unique challenges in terms of trust and attestation. Unlike traditional UEFI modules, which are typically signed by a known vendor or organization, SMM code may be developed internally or by third-party vendors with varying levels of security practices. This can lead to inconsistencies in how SMM code is signed and verified, making it difficult to establish a trusted chain of custody for the code. Furthermore, the absence of a standardized attestation framework for SMM code means that systems may lack the ability to verify the origin and integrity of SMM code in a consistent manner.

Another challenge in SMM code signing and verification is the potential for side-channel attacks or other forms of cryptographic manipulation. If an attacker can exploit weaknesses in the cryptographic algorithms used for SMM code signing, they could potentially forge signatures or intercept verification processes. This is particularly concerning given that SMM code often has access to sensitive system resources and may execute with elevated privileges, making it a prime target for exploitation.

The verification of SMM code also faces challenges related to the dynamic nature of the SMM environment. Unlike static UEFI modules, which are typically loaded once during boot, SMM code may be dynamically updated or extended during system operation. This requires a robust and flexible verification mechanism that can handle these updates without compromising security. However, the limited resources available in the SMM environment may make it difficult to implement such mechanisms effectively.

In summary, the process of signing and verifying SMM code presents a complex set of challenges that stem from the unique characteristics of the SMM environment. These challenges include ensuring the security of private keys, standardizing verification mechanisms, optimizing cryptographic operations for performance, establishing trust in the origin of SMM code, and handling dynamic updates to SMM code. Addressing these challenges requires a combination of robust cryptographic practices, standardized verification protocols, and careful implementation of SMM code signing and verification processes to ensure the integrity and security of the UEFI firmware ecosystem.
